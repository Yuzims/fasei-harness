1. Who decides the next tool?
The LLM. OpenAICompatModel sends all investigation tools with tool_choice: "auto" (src/agent/openai-compat-model.ts). AgentLoop executes whatever name comes back. There is no candidate-action filter on the live path.

The only deterministic chooser is nextInvestigationAction() in src/investigation/test-driver.ts, used only when useTestDriver: true. It is a fixture, not the product agent.

InvestigationStrategy exists (src/domain/types.ts, set by applyRecoveryPlan), but no production LLM code reads context.investigationStrategy / investigationFailure / investigationRecovery. Grep over src/ finds those fields only being passed, never consumed by the model adapter.

3. Does the LLM know which EvidenceRequirements are missing?
Not as structured evaluations, and not during attempt 1.

Requirements are created on the task (defaultResolutionRequirements() in src/domain/factories.ts: req-issue, req-pr, req-commit). They are not listed in the task description or system prompt.

After a failed attempt, the LLM may see opaque IDs in:

lastRecovery.nextStep (e.g. "Gather missing evidence (req-pr, req-commit, commits/repo).")
investigationStrategy.scope (nextRequirementIds copied by strategyFromRecoveryPlan())
That is a string / string-array hint, not evaluateEvidenceRequirement() output.

4. Does RequirementEvaluator participate in investigation, or only verification?
Only verification (and post-attempt failure analysis that copies verifier IDs).

evaluateEvidenceRequirement() is called from:

IndependentCompletionVerifier (src/verification/independent-completion-verifier.ts)
missingRequirements() / evidenceCoverage() / buildVerificationResult() (src/domain/queries.ts)
It is not called from AgentLoop, InvestigationLoopModel, nextInvestigationAction, or tool wrappers.

5. Are verifier results fed back to the Agent?
Only indirectly, after the attempt ends. The verifier runs when loop.run() returns. Attempt 2 sees recovery fields derived from attempt 1’s VerificationResult.missingRequirementIds, not the check list itself. Mid-loop, the agent never sees verified_complete / insufficient_evidence.

6. Are FailureAnalyzer results fed back?
Yes, as state, not as a control signal. applyRecoveryPlan stores state.lastFailure. hint() exposes lastFailureType / lastFailureId. The live model is not required to act on them.

7. What does RecoveryPlanner give the Agent?
A RecoveryPlan plus an InvestigationStrategy:

action (e.g. continue_investigation)
reason, nextStep (prose)
nextRequirementIds
retrievalStrategy (comments / timeline / linked_pr / broaden)
resetEvidence (false for premature_completion)
applyRecoveryPlan (src/investigation/apply-recovery.ts) installs state.investigationStrategy, may change retrievalStrategy, and for continue_investigation / gather_missing_evidence sets claimsRecorded = false. It does not select the next tool.

The test driver does branch on strategy.type (retry_failed_tool, gather_resolution_evidence). The LLM does not.

8. Does the Agent know remaining LLM call budget?
No. LlmRuntimeGuard (src/agent/llm-runtime.ts) only gates HTTP in OpenAICompatModel.assertCanStartCall(). hint() has no llmCallsSent / remaining calls / elapsed ms. Default budget is maxLlmCalls=8, maxWallClockMs=120_000, on top of maxSteps=12 and maxAttempts=3.

9. Does the Agent know which evidence it already has?
Partially. hint().evidence lists summaries; investigatedResources lists keys like issue:1. After attempt reset, compact fields (timeline pullRequestNumbers, comment mention lists, PR semanticReferences) are not in the hint—only coarse summaries such as Timeline for issue #1 (N event(s)).

10. Can it re-fetch low-value information?
Yes, and it still costs an LLM call. wrapGithubTool short-circuits GitHub HTTP when investigatedResources has the key (investigation-tools.ts), returning a compact cached payload. The LLM still had to spend a decide() to choose that tool, then another decide() on the cached result.

11. Can it record_claim before resolution evidence exists?
Yes. record_claim only requires known evidence IDs. It does not check requirements. The system prompt says: if there is no PR, check comments, then stop if evidence is still missing. That matches attempt-1 behavior and conflicts with verifier needs (req-pr, req-commit).

11. Duplicate Investigation Analysis
These four layers are distinct. Phase 8.7.8 hit layer 4, not layer 1.

1. GitHub HTTP deduplication
Almost none at HTTP client. GithubHttpClient retries on retryable errors; it has no ETag/response cache (src/github/http.ts).

Dedup is in wrapGithubTool: same resourceKeyForTool + investigatedResources → no second HTTP, cached: true.

2. Evidence deduplication
addEvidenceOnce() skips if the resource key is already investigated. Phase 8.7.8 kept three evidence IDs; cached get_issue returned the same id. This worked.

3. LLM context duplication
Within an attempt: history grows; formatStateForModel is appended every step (duplicate hint JSON). Across attempts: history reset; hint re-injected. Compact tool results reduced tokens (8.7.5 → 8.7.8) but did not prevent re-choosing cached tools.

4. Investigation action duplication
Not prevented. Nothing forbids the LLM from selecting github_get_issue after issue evidence exists. Cache saves GitHub quota; each such choice still consumes maxLlmCalls. That is the 8.7.8 attempt-2 failure mode.

14. Requirement-driven vs Evidence-gap-driven vs Budget-aware
No ranking “best.” They solve different holes in the current loop.

A. Requirement-driven
Solves: agent ignores req-pr / req-commit during decide().
Needs: task requirements + evaluateEvidenceRequirement (exist).
Adds: a mapping requirement → tools; risk of treating “has_kind” as enough (it is not; req-pr is resolution_candidate, graph-linked).
Alone: still allows re-fetching a satisfied requirement if the map is naive; ignores remaining calls.
B. Evidence-gap-driven
Solves: “what is missing given current evidence”, including satisfied vs missing vs rejected.
Needs: A’s evaluator + current Evidence Graph (exist) + candidate mapping.
Adds: a small projection type and a filter against investigatedResources.
Alone: can still burn 8 calls on a long discovery path if budget is ignored.
C. Budget-aware
Solves: calls 7–8 style waste when maxLlmCalls is the real cap.
Needs: LlmRuntimeGuard.llmCallsSent (exists) + a notion of legal actions (A or B).
Adds: a filter, not a new runtime.
Alone: “spend remaining calls somehow” without knowing the gap — would not have blocked cached get_issue unless combined with B.
Combination
B (gap) = source of truth for “what still matters”
