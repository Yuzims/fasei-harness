# 产品定位与 Phase 20 范围（2026-09-23 审查决议）

## 北极星句（对外唯一表述，所有文案/README 以此为准）

> 一个证据核验型 agent harness：agent 的每一条结论必须绑定可回放的机器证据，做不到就显式降级；失败自动对症恢复。首个场景让用户粘贴任意 GitHub Issue，几分钟内得到「修好了吗 + 每条依据 + 还差什么」。

对外主张的边界（诚实红线）：**不写**「裸 AI 会自信说错」；写「带工具的 AI 也会犯错，且无法区分它哪句查过、哪句在猜——本系统让每条结论强制绑定可复查的机器证据」。此主张由归因评测集实验（见 Phase 20-2）提供数据支撑，若实验结果弱于预期，主张自动收窄至「可审计性」，不硬吹。

## 本体 vs 场景

- **本体**：失败感知运行时（证据图 + verifier 唯一裁决 + 对症恢复）。价值已由 real-v1 benchmark 实证（对症恢复 > 信 Agent / 盲重试，成本更低）。
- **场景**：GitHub Issue 调查。选它因为 GitHub 是天然真值数据集。领域深化（归因不变量、候选呈现）服务于场景可信度，不是产品本体。

## 设计原则：边界诚实

系统对以下情况给出同一形态答案「当前证据无法证明已解决，缺的是 X」，不编造、不含糊：
1. 无效 Issue（模板未填写、无复现信息）→ 「这条报告不构成可查的问题」档结论模板；
2. 修复无记录（静默修复/用户报错 bug）→ 记录层查无实据 + 明示行为验证缺口；
3. 预算内未穷尽 → attributionCoverage 中间结论标。

## 冻结清单（移出当前路线，不删除记录）

- 行为证据通道（沙箱复现）——**冻结理由是工程成本，不是哲学冲突**。解冻时须带负控制协议：脚本先在报告版本复现 bug 成功，才允许用主干不复现裁「已修复」；脚本本体按 hypothesis 存档。
- `templateEmptiness` 机械模板比对、`releaseDate(testedVersion)` npm registry 查询——并入行为证据解冻时一起做。
- 多 tracker（GitLab/Jira）、多语言 i18n、生产级鉴权/部署。
